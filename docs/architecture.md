# How Gui works

The architecture, one part at a time, with the files to read for each. The [README](../README.md) has the overview and the security model.

```
BrowserWindow (window.ts)
├─ app chrome (React)         tab strip, toolbar, canvas states, drawer (logs, terminals)
└─ active tab (tab.ts)        one project; other tabs' views are out of the window, still running
   ├─ WebContentsView: preview   your app at localhost, sandboxed, no preload
   └─ WebContentsView: chat      floating, transparent, draggable panel (React)
```

The preview is a native view, so HTML can't overlay it: the chat panel is its own transparent view stacked on top, moved by the main process as you drag it. Each tab owns its views, dev server, agent and preview tools; switching tabs swaps which tab's views are in the window and whose state the chrome shows.

- **Dev server** (`src/main/dev-server.ts`): runs the dev script in a PTY through your login shell, detects the printed URL, and only marks it ready once a listener in *its own process group* owns the port. If another project's server shadows `localhost` on the other address family, the preview pins to `127.0.0.1` or `[::1]`.
- **Terminals** (`src/main/terminals.ts`, `src/renderer/src/app/drawer.tsx`): each is your login shell (`$SHELL -l`) in a PTY at the project root, with your login-shell environment, started when you open it. Keystrokes come only from the window's own chrome (never the chat panel, which renders what agents write) and only for the shown project's terminals; main keeps the last 512 KB of each one's output so the drawer can draw it again after you switch tabs. Output (the dev server's too) streams only to the drawer tab on screen, one message per frame or per 256 KB (`src/main/output.ts`): the drawer acknowledges what it has drawn, and a shell printing faster than that waits for it (node-pty stops reading; typing, ⌃C among it, still gets through), like any terminal that can't keep up, though never for long on a drawer that isn't drawing. Out of sight, shells and the dev server go on unheld, and the drawer catches up from what main kept when it shows them. Closing a terminal, its tab or window, or quitting hangs up on the shell and every process group on its terminal or started from it (job control gives each job its own), then kills whatever is left after half a second. Agents don't see terminal output.
- **Device frames** (`src/main/viewport.ts`): Chromium's device emulation (`Emulation.setDeviceMetricsOverride` over the inspector's debugger session) lays the page out at the frame's CSS size and draws it scaled into a view that size times the scale, the way DevTools' device mode fits a device to its window. A canvas frame no device's width matches opens in a frame of its own size the same way (viewport id `1080x1080`, `frameViewport` in `src/shared/types.ts`), not a touch device; only the open frame's size can be chosen besides the four devices. Tablet and Mobile are emulated as mobile devices (`<meta name=viewport>` applies, scrollbars overlay, touch media queries match) while the mouse stays a mouse, so picking and hover work as usual. Picking, the floating chat, crops and screenshots map page coordinates through the scale; screenshots are the page at its CSS size, in the display's pixels.
- **Motion** (`src/shared/motion.ts`): anything you drag or throw moves on springs (Apple's damping-ratio and response parametrisation, solved exactly so any frame rate works), started from where it is and as fast as it's going, so every animation can be caught or redirected. Critically damped by default; a throw's spring overshoots a little, and the landing spot is projected from the release velocity the way a scroll view decelerates. The floating chat is a native view, so main steps its springs at the display's refresh rate (`src/main/panel-flight.ts`); its panel, pill and bubble morph into one another in the chat view, which tells main when to shrink the view. Chat state changes (a message sent or starting from the queue, a permission answered) are view transitions. The preview's own layout changes (another viewport, a zoom step, the drawer, docking the chat, focus mode) resize the live page rather than jump (`src/main/preview-morph.ts`, `src/renderer/src/app/layout-morph.ts`), the way dragging a window's edge would: main springs the view's bounds and its emulated viewport together on the display's frames, so your app lays itself out again at every size on the way, and the chrome draws the device frame and its label around it. A change mid-motion carries on from wherever it is, keeping its speed. The drawer and the toolbar slide on the same spring, and the docked chat slides in over the page. Dragging the chat to an edge docks it there (`src/main/dock-target.ts` shows where, a small view of its own over the preview and under the chat); pulling the sidebar's header undocks it, and the floating panel follows the pointer in window coordinates while the canvas widens under it. With Reduce motion on, nothing moves or scales: things jump into place, and short cross-fades stand in where something appears or goes.
- **Selection** (`src/main/picker.ts`, `inspector.ts`, `src/renderer/src/pick`): while you pick, a transparent view of Gui's own lies over the preview and draws the outlines, labels and the area you drag, so nothing is injected into your DOM. Its pointer goes to main, which finds the element there with the Chrome DevTools Protocol (`DOM.getNodeForLocation`) and measures it (`DOM.getBoxModel`); the wheel is passed on to the page as precise scroll deltas, so it scrolls as smoothly as it would directly. HTML, attributes, computed styles, and the box come from protocol commands that page scripts can't spoof; only the React owner chain (and the component name on the hover label) is read from the page, and it's validated. An area is captured from the page and described by the smallest element around it. Everything picked is sent to the agent marked as untrusted.
- **Source mapping** (`src/main/source-resolver.ts`): React 19 records where each JSX element was created (`_debugStack`); Gui resolves that frame through the dev server's source maps to `file:line`. Exact for Vite and Next.js (Turbopack); approximate for Next.js (webpack). Astro pages map through the `data-astro-source-file`/`-loc` attributes its dev server adds. Server-rendered pages wait for hydration before reading fibers. Source-map fetching, parsing, and lookup run in a bounded background worker, so large maps do not block the main process while picking.
- **Agents** (`src/main/agents.ts`, `agent.ts`, `agent-status.ts`, `chat.ts`): spoken to over the [Agent Client Protocol](https://agentclientprotocol.com). Claude Code, Codex, Pi, Muse Code, and Amp run through bundled adapters (`@agentclientprotocol/claude-agent-acp`, `@agentclientprotocol/codex-acp`, `pi-acp`, `@bex-co/muse-code-acp`, `amp-acp`) on Electron's Node. Gui doesn't ship the Claude Code and Codex CLIs those adapters drive (`src/main/agent-binaries.ts`): it uses your own install when its version matches what the adapter was built for, and otherwise **Install** downloads that exact version from npm, checks it against the hash pinned in `bun.lock`, and keeps it in Gui's data folder (your own install is left alone); Grok Build, Kiro, OpenCode, Devin, Cursor, and jcode speak ACP themselves and are found on your login-shell PATH, as are the `pi`, `muse`, and `amp` CLIs their adapters drive. Pi and jcode don't get Gui's preview tools: Pi's adapter doesn't pass MCP servers through, and jcode uses only the MCP servers in its own config. jcode has no login; until its first-run setup (`jcode` in a terminal) has written `~/.jcode/config.json`, its sessions fail, and Gui offers that setup as its sign-in. On launch Gui checks the bundled agents and the one you picked by starting (but not prompting) a session; **Check again** on the start screen checks every installed agent. The project's **Ask** or **Auto** also sets the agent's own permission mode (declared per agent in `agents.ts`), when a session starts or resumes and when you switch: Claude Code gets Manual or Auto (Accept edits when its model has no Auto), Codex Read-only or Auto review, jcode Ask for approval or Auto (its LLM reviewer allows safe calls and asks about uncertain ones), and Muse Code On request (with Muse 1.2.1+'s `promptUnmatched` approval policy) or Auto-approve. Grok Build has no ACP modes and takes it as session `_meta` (Ask: `yoloMode` and `autoMode` off; Auto: `autoMode`), so switching resumes its session before the next message. Gui only sets modes the session offers, and leaves the mode alone in between, so a mode you or the agent pick another way stays until the next switch; the chat header shows the current one. Kiro, OpenCode, Pi, Amp, Devin, Cursor and custom agents keep the permission mode your own agent config picks. Amp's adapter keeps its configured permissions in both Ask and Auto; Amp runs tools without prompts by default unless its permissions are configured. The adapter doesn't support resuming after an app restart. Cursor runs through its `cursor-agent` alias so it can't collide with another CLI named `agent`. Cursor plan approvals appear in chat; its custom question forms are skipped with a request to ask in normal chat instead. Each agent's own config (CLAUDE.md, hooks, Codex/OpenCode/Pi settings, …) applies as usual. When the agent asks, Gui approves edits to ordinary source files in the project and, in **Ask** mode, asks you in the chat about everything else. In **Auto** mode (`src/main/auto-approve.ts`) it also approves commands, fetches, and reads, picking only one-time approvals; it still asks when a request names a file outside the project, edits a sensitive file (config, dotfiles, lockfiles, scripts, `package.json`, git hooks), changes the agent's mode or plan, or the agent itself flags it (Claude's own ask rules and safety checks). Commands aren't sandboxed: Auto trusts the agent's commands the way its own auto modes do.
- **Preview tools for the agent** (`src/main/mcp-server.ts`, `preview-tools.ts`, `preview-interactions.ts`): each tab serves an MCP server on loopback (random port, bearer token) that Gui passes to every agent session that accepts HTTP MCP servers. Agents can `preview_screenshot` (an element, the full page, or at a viewport width like 390), `preview_inspect` (computed styles, box, and source file for a selector), `preview_snapshot` (page text and controls with unique CSS selectors), `preview_console`, `preview_navigate`, `preview_reload`, and `dev_server_logs`. `preview_click`, `preview_hover`, `preview_type`, `preview_press`, and `preview_scroll` send real Chromium input, including React input handlers and nested scrolling, in the same preview the user sees. They reject ambiguous, hidden, or covered targets; clicking and typing also reject disabled targets. `preview_variations` shows versions of an element the agent wrote behind a small switch, with a bar beside it to flip them ([Variations](variations.md)). Snapshots list the main document, without iframe or shadow-root contents. Agents are instructed to edit, view and exercise the result, then revise and recheck within the same turn before replying. Resumed sessions receive updated instructions once when the guidance changes.
- **Canvases** (`src/main/board.ts`, `board-session.ts`, `mcp-board-tools.ts`, `src/renderer/src/app/board.tsx`): a canvas is a folder in Gui's data (`canvases/<id>/`): `canvas.json` (each frame's name, place and size, and where the board was looking), `frames/<id>.html`, and `assets/` for shared images. Being a real folder, its chat history, checkpoints and Ask/Auto work as a project's do; nothing runs but the agent. The tab keeps the manifest in step with the files whoever writes them: a page the agent writes directly joins the board, one deleted leaves it, and an undone turn puts both back. Frames are served to the preview from a per-canvas loopback server (random port, token path, confined to the canvas folder, never the manifest) at `http://<canvas id>.localhost:<port>`, which Chromium resolves to loopback itself: a site of its own, so a frame shares no cookies with your apps on `localhost` or `127.0.0.1` in the preview's session (cookies ignore ports), and the server answers no other host, and captured offscreen as thumbnails whenever their page changes; the board loads those through Gui's own `gui-thumb:` protocol, which previewed pages can't reach. In a canvas the agent gets a canvas preamble instead of the dev-server rules, a block each turn listing the frames with what's selected and open, and canvas tools: `canvas_list_frames`, `canvas_create_frame` (placed beside what it varies, never overlapping), `canvas_duplicate_frames`, `canvas_arrange_frames`, `canvas_rename_frame`, `canvas_delete_frames`, `canvas_screenshot`, and `canvas_open_frame`, which shows a frame live so the preview tools work on it.
- **Errors** (`src/main/problems.ts`): console errors since the last navigation and dev-server build errors since the last successful rebuild show above the composer with a **Fix** button, and ride along with every prompt as untrusted context.
- **Recordings** (`src/main/recordings.ts`, `src/renderer/src/app/record-button.tsx`): the toolbar starts a display-media stream of the preview’s own frame, never a screen or window. MediaRecorder saves WebM video; decoded frames are sampled at up to 30 fps as JPEGs with actual media timestamps. Encoding or disk backpressure may leave gaps, which the frame timing reports. Clips and frames live under the project’s recording directory in Gui’s app data. `recording_info` returns timing, `recording_frame` retrieves a zero-based captured frame, and `recording_frames` samples a time range (at most 12 images per response). Unsent clips are deleted when removed or the project closes; sent clips survive restarts, and Clear chat history also clears recordings for closed projects.
- **History** (`src/main/history.ts`): each project's transcript, checkpoints, and agent session are saved, so after a restart the chat is still there, old turns can still be undone, and the agent resumes its session (ACP `session/load`) with its memory.
- **Settings** (`src/main/settings.ts`, `src/renderer/src/settings/`): a separate window (⌘,) for switching agents on and off, signing in, adding custom agents, the default agent and chat docking, revoking trusted projects, clearing recent projects, and clearing chat history, checkpoints, and preview site data. Projects open in a tab keep their chat history and checkpoints when those are cleared.
- **Checkpoints** (`src/main/checkpoints.ts`): before and after every turn the working tree is snapshotted into a shadow git repo under the app's data folder (your `.git` is never touched). **Undo** restores the files that turn (and any later ones) changed to how they were before it; files you edited yourself are left alone. **Redo** reverses the undo.
