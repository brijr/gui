# How Gui works

The architecture, one part at a time, with the files to read for each. The [README](../README.md) has the overview and the security model.

```
BrowserWindow (window.ts)
├─ app chrome (React)         tab strip, toolbar, canvas states, drawer (logs, terminals)
└─ active tab (tab.ts)        one project; other tabs' views are out of the window, still running
   ├─ WebContentsView: preview   your app at localhost, sandboxed, with a small preload of its own
   └─ WebContentsView: chat      floating, transparent, draggable panel (React)
```

The preview is a native view, so HTML can't overlay it: the chat panel is its own transparent view stacked on top, moved by the main process as you drag it. Each tab owns its views, dev server, agent and preview tools; switching tabs swaps which tab's views are in the window and whose state the chrome shows. Chromium goes on drawing a page whose view is hidden or out of its window, so main tells a chat page when nobody can see it (its tab in the background, the chat hidden, its window minimized or hidden: `syncSeen` in `src/main/tab-chat-panel.ts`): it still takes in every update, and holds its spinners and its Working count until someone can. The preview is left alone: agents work on background tabs and need its frames.

The preview never gets the preload Gui's own UI uses (`src/preload/index.ts`). Its own (`src/preload/preview.ts`) runs in an isolated world and exposes nothing to the page: no `contextBridge` API, no globals. It listens to the page's events and sends main four messages (`src/shared/preview-text.ts`, `preview-guides.ts`), for **Text edit** and **Rulers and guides** below. Main (`src/main/index.ts`, `previewTab`) takes them only from the top frame of a view that a tab owns as its preview (`ProjectTab.ownsPreview`), and checks each argument: finite numbers, and text of at most 4,000 characters. The README's security model has the rest.

- **Dev server** (`src/main/dev-server.ts`): runs the dev script in a PTY through your login shell, detects the printed URL, and only marks it ready once a listener in *its own process group* owns the port. If another project's server shadows `localhost` on the other address family, the preview pins to `127.0.0.1` or `[::1]`.
- **Terminals** (`src/main/terminals.ts`, `src/renderer/src/app/drawer.tsx`): each is your login shell (`$SHELL -l`) in a PTY at the project root, with your login-shell environment, started when you open it. Keystrokes come only from the window's own chrome (never the chat panel, which renders what agents write) and only for the shown project's terminals; main keeps the last 512 KB of each one's output so the drawer can draw it again after you switch tabs. Output (the dev server's too) streams only to the drawer tab on screen, one message per frame or per 256 KB (`src/main/output.ts`): the drawer acknowledges what it has drawn, and a shell printing faster than that waits for it (node-pty stops reading; typing, ⌃C among it, still gets through), like any terminal that can't keep up, though never for long on a drawer that isn't drawing. Out of sight, shells and the dev server go on unheld, and the drawer catches up from what main kept when it shows them. Closing a terminal, its tab or window, or quitting hangs up on the shell and every process group on its terminal or started from it (job control gives each job its own), then kills whatever is left after half a second. Agents don't see terminal output.
- **Device frames** (`src/main/viewport.ts`): Chromium's device emulation (`Emulation.setDeviceMetricsOverride` over the inspector's debugger session) lays the page out at the frame's CSS size and draws it scaled into a view that size times the scale, the way DevTools' device mode fits a device to its window. A canvas frame no device's width matches opens in a frame of its own size the same way (viewport id `1080x1080`, `frameViewport` in `src/shared/types.ts`), not a touch device; only the open frame's size can be chosen besides the four devices. Tablet and Mobile are emulated as mobile devices (`<meta name=viewport>` applies, scrollbars overlay, touch media queries match) while the mouse stays a mouse, so picking and hover work as usual. Picking, the floating chat, crops and screenshots map page coordinates through the scale; screenshots are the page at its CSS size, in the display's pixels.
- **Motion** (`src/shared/motion.ts`): anything you drag or throw moves on springs (Apple's damping-ratio and response parametrisation, solved exactly so any frame rate works), started from where it is and as fast as it's going, so every animation can be caught or redirected. Critically damped by default; a throw's spring overshoots a little, and the landing spot is projected from the release velocity the way a scroll view decelerates. The floating chat is a native view, so main steps its springs at the display's refresh rate (`src/main/panel-flight.ts`); its panel, pill and bubble morph into one another in the chat view, which tells main when to shrink the view. Chat state changes (a message sent or starting from the queue, a permission answered) are view transitions. The preview's own layout changes (another viewport, a zoom step, the drawer, docking the chat, focus mode) resize the live page rather than jump (`src/main/preview-morph.ts`, `src/renderer/src/app/layout-morph.ts`), the way dragging a window's edge would: main springs the view's bounds and its emulated viewport together on the display's frames, so your app lays itself out again at every size on the way, and the chrome draws the device frame and its label around it. A change mid-motion carries on from wherever it is, keeping its speed. The drawer and the toolbar slide on the same spring. Docking and undocking (⇧⌘D, dragging the chat to an edge, pulling the sidebar's header) change the chat's shape rather than swap it: main springs it between the floating card and the sidebar (`src/main/dock-morph.ts`), its bounds, corners and shadow together, on the preview's spring and from the frame the preview starts moving, so the two move as one; an offset on its own spring takes up a release's speed and any jump in where the ends are, so it can be turned back mid-way. The chat view is sized to the shape each frame and the chat page is told how to draw it in there (`ChatShape`) just before, keyed to that size so they never disagree. The sidebar shown on ⌘B still slides in over the page. While dragging, `src/main/dock-target.ts` shows where the sidebar would go (a small view of its own over the preview and under the chat), and the card dropped there grows over it; held, the floating panel follows the pointer in window coordinates while the canvas changes under it. With Reduce motion on, nothing moves or scales: things jump into place, and short cross-fades stand in where something appears or goes.
- **Selection** (`src/main/picker.ts`, `inspector.ts`, `src/renderer/src/pick`): while you pick, a transparent view of Gui's own lies over the preview and draws the outlines, labels and the area you drag, so nothing is injected into your DOM. Its pointer goes to main, which finds the element there with the Chrome DevTools Protocol (`DOM.getNodeForLocation`) and measures it (`DOM.getBoxModel`); the wheel is passed on to the page as precise scroll deltas, so it scrolls as smoothly as it would directly. HTML, attributes, computed styles, and the box come from protocol commands that page scripts can't spoof; only the React owner chain (and the component name on the hover label) is read from the page, and it's validated. An area is captured from the page and described by the smallest element around it. Everything picked is sent to the agent marked as untrusted.
- **Source mapping** (`src/main/source-resolver.ts`): React 19 records where each JSX element was created (`_debugStack`); Gui resolves that frame through the dev server's source maps to `file:line`. Exact for Vite and Next.js (Turbopack); approximate for Next.js (webpack). Astro pages map through the `data-astro-source-file`/`-loc` attributes its dev server adds. Server-rendered pages wait for hydration before reading fibers. Source-map fetching, parsing, and lookup run in a bounded background worker, so large maps do not block the main process while picking.
- **Text edit** (`src/preload/preview.ts`, `src/main/text-edit.ts`, `startTextEdit` and `endTextEdit` in `src/main/tab.ts`): in design mode, double-click text in the preview to edit it where it is; Return or clicking away keeps it, Esc puts it back, as a hint beside it says. The first click picks at once and ends design mode, but the pick overlay stays over the spot it picked, unseen, for the Mac's double-click interval (`Picker.lingerOnStop`), so a click anywhere else reaches the page; a second click on the same spot makes it a double-click: main drops the pick the first click made (the selection goes back to what it was) and and asks the preview's preload for the text at that point (`editTextAt`, `PreviewText.begin`); the preload makes the element editable and tells main what the text said, and main finds the element there with the DevTools protocol, before typing moves it. A double-click in the page itself is the page's. It works on your app at a local address and on an open canvas frame, one edit at a time. Both texts, and the file that wrote the element, come from the page, so main trusts none of them (the README's security model has the reasoning). When the edit ends, main rewrites the text (`ChatController.writeTextEdit`: a turn of the user's own, with `editedFile`, checkpointed before and after like an agent's, so the chat shows it in one line with Undo) in the file that rendered the element (a canvas frame's own page) only as plain text for plain text (`replaceText`): the file is JSX, Astro or HTML; the old text is all one element holds there, between its own tags, once, or once within 12 lines below where the element was written; and neither text holds anything that isn't literal wherever markup can sit. Copy in a string literal or an attribute goes to the agent. Otherwise, or while a turn is running, the agent is asked for the change, with the element picked: the turn's message is Gui's fixed "Change this text." (`TEXT_EDIT_PROMPT`), and the two texts ride on the turn and on a queued message as `textEdit`, apart from its text. The transcript and the queue show them beside the message; the agent gets them in a fenced `<text_edit_…>` block (`describeTextEdit` in `src/main/prompt.ts`).
- **Rulers and guides** (`src/main/guides.ts`, `guide-alignment.ts`, `src/renderer/src/app/rulers.tsx`, `src/renderer/src/guides-main.ts`): ⇧R, the toolbar's Rulers button or View → Rulers shows rulers along the top and left of a project's preview, in the page's CSS pixels. Dragging out of a ruler makes a guide; dragging a guide back onto its ruler removes it. A dragged guide snaps to the nearest edge or middle of the element under the pointer when one is within 5px. Main keeps the guides in page pixels, per project, in prefs (up to 50), and moves them as the page scrolls, which the preview's preload reports. It tells the chrome what the rulers show only when that changes; rulers drawn anew (with each tab shown, or the window's page loaded again) ask. Each guide is drawn by a thin view of its own over the preview, so nothing is added to your page's DOM, screenshots or recordings. While the rulers show, every prompt names the guides' positions, and `preview_guides` gives the agent the element edges within 8px of a guide but not on it, and lets it add or remove guides. A canvas has no rulers.
- **Agents** (`src/main/agents.ts`, `agent.ts`, `agent-status.ts`, `chat.ts`): spoken to over the [Agent Client Protocol](https://agentclientprotocol.com). Claude Code, Codex, Pi, Muse Code, and Amp run through bundled adapters (`@agentclientprotocol/claude-agent-acp`, `@agentclientprotocol/codex-acp`, `pi-acp`, `@bex-co/muse-code-acp`, `amp-acp`) on Electron's Node. Gui doesn't ship the Claude Code and Codex CLIs those adapters drive (`src/main/agent-binaries.ts`): it uses your own install when its version matches what the adapter was built for, and otherwise **Install** downloads that exact version from npm, checks it against the hash pinned in `bun.lock`, and keeps it in Gui's data folder (your own install is left alone); Grok Build, Kiro, OpenCode, Devin, Cursor, fx, jcode, and Gemini CLI speak ACP themselves and are found on your login-shell PATH, as are the `pi`, `muse`, and `amp` CLIs their adapters drive. Pi and jcode don't get Gui's preview tools: Pi's adapter doesn't pass MCP servers through, and jcode uses only the MCP servers in its own config. jcode has no login; until its first-run setup (`jcode` in a terminal) has written `~/.jcode/config.json`, its sessions fail, and Gui offers that setup as its sign-in. On launch Gui checks the bundled agents and the one you picked by starting (but not prompting) a session; **Check again** in Settings → Agents checks every installed agent. The project's **Ask** or **Auto** also sets the agent's own permission mode (declared per agent in `agents.ts`), when a session starts or resumes and when you switch: Claude Code gets Manual or Auto (Accept edits when its model has no Auto), Codex Read-only or Auto review, jcode Ask for approval or Auto (its LLM reviewer allows safe calls and asks about uncertain ones), Gemini CLI Default for both (its Auto Edit and YOLO approve without asking, so Gui's rules would never see those requests), and Muse Code On request (with Muse 1.2.1+'s `promptUnmatched` approval policy) or Auto-approve. Grok Build has no ACP modes and takes it as session `_meta` (Ask: `yoloMode` and `autoMode` off; Auto: `autoMode`), so switching resumes its session before the next message. Gemini CLI reports a mode change, its own (entering Plan) or Gui's, as a `[MODE_UPDATE] <mode>` message; Gui reads that as the mode change and keeps it out of the chat. Gui only sets modes the session offers, and leaves the mode alone in between, so a mode you or the agent pick another way stays until the next switch; the chat header shows the current one. fx, Amp, OpenCode, Pi and Kiro keep their own setting (`ownPermissions` in `agents.ts`): Gui can't switch them to a mode that asks first, so the chat shows "fx's own setting" (with the agent's name) where Ask and Auto would be, and Gui's Auto doesn't answer for them: beyond edits to ordinary project files, what one asks comes to you in the chat. An agent whose session doesn't offer the mode Ask wants is treated the same way (`src/main/permission-modes.ts`). Devin, Cursor and custom agents declare no modes, so Gui sets none and the mode your own agent config picks stays. Amp runs tools without prompts by default unless its permissions are configured. Amp chats resume after an app restart (amp-acp 0.12). Cursor runs as `cursor-agent`, or as `agent` when that command's real path is Cursor's (`src/main/executables.ts`), since other CLIs install an `agent` too. Cursor plan approvals appear in chat; its custom question forms are skipped with a request to ask in normal chat instead. Each agent's own config (CLAUDE.md, hooks, Codex/OpenCode/Pi settings, …) applies as usual. When the agent asks, Gui approves edits to ordinary source files in the project and, in **Ask** mode, asks you in the chat about everything else. In **Auto** mode (`src/main/auto-approve.ts`) it also approves commands, fetches, and reads, picking only one-time approvals; it still asks when a request names a file outside the project, edits a sensitive file (build, tool and deploy config, dotfiles, dependency manifests and lockfiles, scripts, Dockerfiles, git hooks), changes the agent's mode or plan, or the agent itself flags it (Claude's own ask rules and safety checks). Commands aren't sandboxed: Auto trusts the agent's commands the way its own auto modes do.
- **Skills and slash commands** (`src/shared/commands.ts`, `src/main/skills.ts`, `src/renderer/src/chat/command-menu.tsx`): typing `/` in the message box lists the agent's commands, as its session reports them (ACP `available_commands_update`). A slash command goes at the start of the message. Ones that act on the session itself (`/clear`, `/model`, `/compact` and the like) are sent alone, without the picked element or images; the rest take the message's context along. Claude Code, Codex, Grok Build, Muse Code and Pi list their skills there themselves. OpenCode and fx don't, but load a skill when the message names it, so Gui finds the skills in the folders each of them reads, in the project and in your home folder, and lists those: OpenCode's are written into the message in words ("Use the … skill"), fx's as `$name`, or in words when the name has a space.
- **Preview tools for the agent** (`src/main/mcp-server.ts`, `mcp-preview-tools.ts`, `mcp-app-tools.ts`, `preview-tools.ts`, `preview-interactions.ts`): each tab serves an MCP server on loopback (random port, bearer token) that Gui passes to every agent session that accepts HTTP MCP servers. Agents can `preview_screenshot` (an element, the full page, or at a viewport width like 390), `preview_inspect` (computed styles, box in page pixels, and source file for a selector; `states` adds the styles it has on hover, focus or press), `preview_snapshot` (page text and controls with unique CSS selectors), `preview_console`, `preview_navigate` (a path on your app), `preview_open_website` (a public website's full address, which you're asked to allow: see **Websites in the preview**; not offered to Amp, fx, Kiro, OpenCode or Pi, whose own settings decide what they ask, so Gui can't make them ask first), `preview_back`, `preview_reload`, and `preview_wait` (until an element or text shows or goes away, up to 15 seconds). `dev_server_logs` says whether your app is installing, starting, running or stopped and how Gui starts it, then its latest output; `dev_server_restart` starts it again, installing dependencies if they're missing, and waits up to a minute; `set_start_command` changes the command Gui starts it with, once you approve it. `preview_click`, `preview_hover`, `preview_type`, `preview_press`, and `preview_scroll` send real Chromium input, including React input handlers and nested scrolling, in the same preview the user sees. They reject ambiguous, hidden, or covered targets; clicking and typing also reject disabled targets. `preview_point` walks you through the page one step per call: a pointer you can see moves to an element, which is outlined with a caption beside it; the input tools move the same pointer to their target first. While you watch, the agent's input moves as a person's would (`input-pace.ts`): the pointer glides on from where it last was, the page eases to a target that's out of view as the pointer heads there, text arrives a few characters at a time (within 0.8 seconds however long it is), the wheel slows to a stop, and a key pressed shows on the pointer. With Reduce motion, or the page out of sight, each lands at once. The events themselves are the same either way. `preview_variations` shows versions of an element the agent wrote behind a small switch, with a bar beside it to flip them ([Variations](variations.md)). `preview_motion` (`preview-motion.ts`) plays motion in your app (a click, hover, key or scroll, a replay of the page's CSS and Web Animations, a reload, or nothing) and films it: one contact-sheet image of up to 12 timed frames over up to 5 seconds, and a timeline of the animations that ran, traced as a recording's is; it can slow CSS and Web Animations down (CDP `Animation.setPlaybackRate`) and emulate `prefers-reduced-motion`, both undone afterwards. JavaScript-driven motion shows in the frames, not as an animation in the timeline. `preview_guides` reads your ruler guides with the element edges that just miss them, and adds or removes guides (see **Rulers and guides**). Those two, `preview_open_website`, `preview_back` and the dev server tools are offered in a project, not in a canvas, whose page tools act on the frame it has open. `chat_turns` lists the chat's earlier messages, whether each was undone, and the files each changed; it changes nothing. The recording tools are under **Recordings**. Snapshots list the main document, without iframe or shadow-root contents. Agents are instructed to edit, view and exercise the result, then revise and recheck within the same turn before replying. Resumed sessions receive updated instructions once when the guidance changes.
- **Websites in the preview** (`src/main/website.ts`, `web-session.ts`, `public-address.ts`, `public-proxy.ts`, `web-capture.ts`): `preview_open_website` opens a public website in the preview's place, over your app, so the agent can use it like a user with the same page tools. It is a view of its own with no preload, in an in-memory session apart from the preview's, wiped before it's used and again when the website closes, so it has none of your sign-ins. The session grants no permissions and refuses downloads and form posts. Every connection goes through a loopback SOCKS5 proxy that looks each name up itself and connects only to the public address it checked, so a page can't reach this Mac or the local network. On a website, typing refuses password, one-time code and payment fields, and inspect never shows what's in a field. While the agent's turn uses the website, your pointer and keys don't reach it; the address bar shows its address, and **Back to your app** or your next message closes it. A canvas doesn't open websites this way: `canvas_screenshot_url` captures one in a hidden window, in a session locked down the same way.
- **Canvases** (`src/main/board.ts`, `board-session.ts`, `mcp-board-tools.ts`, `src/renderer/src/board/`): a canvas is a folder in Gui's data (`canvases/<id>/`): `canvas.json` (each frame's name, place and size, and where the board was looking), `frames/<id>.html`, and `assets/` for shared images. Being a real folder, its chat history, checkpoints and Ask/Auto work as a project's do; nothing runs but the agent. The tab keeps the manifest in step with the files whoever writes them: a page the agent writes directly joins the board, one deleted leaves it, and an undone turn puts both back. Frames are served to the preview from a per-canvas loopback server (random port, token path, confined to the canvas folder, never the manifest) at `http://<canvas id>.localhost:<port>`, which Chromium resolves to loopback itself: a site of its own, so a frame shares no cookies with your apps on `localhost` or `127.0.0.1` in the preview's session (cookies ignore ports), and the server answers no other host, and captured offscreen as thumbnails whenever their page changes; the board loads those through Gui's own `gui-thumb:` protocol, which previewed pages can't reach, and which Gui's own pages can `fetch` with CORS, as a WebGL texture needs. The board is `src/renderer/src/board/`, a WebGL2 canvas with a DOM overlay. The canvas (`surface.tsx`, drawing on demand, at most once a frame) draws its pixels: the dot grid, section areas, frames and their thumbnails, what's selected, the resize handle and the marquee, from the quads `scene.ts` makes of the board and the camera; `gl/renderer.ts` draws them, `gl/textures.ts` holds one texture a frame at the width it's drawn (the smaller widths decoded from a 360px copy, under a byte budget, replaced 120 ms after a zoom rests, never blank between), and `gl/theme.ts` reads its colours from the page's CSS variables. Without WebGL2, or when the GPU context is lost and not given back within five seconds, the board says it can't be shown; there is no other way to draw it. `board.tsx` is a shell that owns the camera (`use-camera.ts`) and the gesture under way, and does what plain functions say: the camera's arithmetic (pan, zoom about a point, fit, reveal, the marquee) in `camera.ts`, in the board and board-view pixels of `src/shared/coords.ts`; what a press, drag and release do in `gestures.ts`; what a key does in `keys.ts`; what is near enough the view to mount, and which names have room, in `scene.ts`. `intents.ts` is the one place it calls `window.gui`; `overlay.tsx` is the DOM over the canvas, in a layer the camera moves: names, rename fields, the live region, and a transparent tile per frame (and the handle's grip), which is what a press lands on and what specs find; each tile is an `option` named for its frame and the board's `aria-activedescendant` is the frame last selected, so a screen reader follows Tab, and each says which texture width the canvas holds for it (`data-thumb`). `view.ts` shares its zoom and Move/Hand tool with the toolbar. [webgl-board](webgl-board/README.md) has the measurements and decisions behind drawing it this way. In a canvas the agent gets a canvas preamble instead of the dev-server rules, a block each turn listing the frames with what's selected and open, and canvas tools: `canvas_list_frames`, `canvas_create_frame` (placed beside what it varies, never overlapping), `canvas_duplicate_frames`, `canvas_arrange_frames` (move, resize or rename), `canvas_delete_frames`, `canvas_screenshot`, `canvas_section` (creates, updates or deletes a named group of frames; deleting one leaves its frames), `canvas_screenshot_url` (a screenshot of any public website, optionally saved to the canvas's `assets/`; see **Websites in the preview**), and `canvas_open_frame`, which shows a frame live so the preview tools work on it.
- **Errors** (`src/main/problems.ts`): console errors since the last navigation and dev-server build errors since the last successful rebuild show above the composer with a **Fix** button, and ride along with every prompt as untrusted context.
- **Recordings** (`src/main/recordings.ts`, `recording-trace.ts`, `src/renderer/src/app/record-button.tsx`): the toolbar starts a display-media stream of the preview’s own frame, never a screen or window. MediaRecorder saves WebM video; decoded frames are sampled as JPEGs with actual media timestamps. A clip runs up to 60 seconds with frames at up to 30 fps; a narrated one runs up to 3 minutes with frames at up to 10 fps (the limits are in `src/shared/bounded.ts`). Encoding or disk backpressure may leave gaps, which the frame timing reports. Clips and frames live under the project’s recording directory in Gui’s app data. `recording_frames` samples a time range or retrieves zero-based captured frames by index (at most 12 images per response), `recording_timeline` gives the clip's size, length and frame timing, then a log of what happened in the page while it was recorded (your clicks, keys and scrolls, animations and transitions, layout shifts, slow frames), and `recording_narration` reads what you said with where the pointer was. Unsent clips are deleted when removed or the project closes; sent clips survive restarts, and Clear chat history also clears recordings for closed projects.
- **Narration** (`src/renderer/src/app/recording-voice.ts`, `src/main/transcribe.ts`, `recording-narration.ts`, `recording-cursor.ts`, `recording-prompt.ts`, `native/transcribe/main.swift`): with Record with Voice (Record's menu; ⌥⌘R repeats the last choice), you talk and point while you record. Main asks macOS for the microphone and allows one audio request, from Gui's own window, for that recording; the preview never gets the microphone. The voice goes into the clip, which plays back with sound and captions, and is transcribed on this Mac by Apple's SpeechAnalyzer (macOS 26 or later) through the `gui-transcribe` helper. The audio kept for that is deleted once it's transcribed, and nothing leaves the machine. Main also tracks the pointer over the preview: where it was, where it held still, and what element it was on. The agent gets what you said as part of your request, each sentence paired with where the pointer was, and up to 8 frames chosen at pointing words ("this", "here"), where the pointer held still, clicks, and the middle of sentences.
- **History** (`src/main/history.ts`): each project's transcript, checkpoints, and agent session are saved, so after a restart the chat is still there, old turns can still be undone, and the agent resumes its session (ACP `session/resume` when the agent offers it, otherwise `session/load`) with its memory.
- **Settings** (`src/main/settings.ts`, `src/renderer/src/settings/`): a separate window (⌘,) with six sections. **Agents**: switching agents on and off, signing in, adding custom agents, and the default agent (**Use** on its row); agents not checked yet are checked as the section opens. **Chat**: where the chat sits (floating, left or right). **Projects**: revoking trusted projects, resetting a dev server command you set, and clearing recent projects. **GitHub**: connecting or disconnecting GitHub and choosing the repositories Gui can see, for cloning. **Storage**: clearing chat history, undo history (checkpoints), and preview site data. **Account**: who's signed in, product-update emails, signing out, and whether crash reports are sent. Projects open in a tab keep their chat history and checkpoints when those are cleared.
- **Accounts** (`src/main/account.ts`, `account-ipc.ts`, `github.ts`, `clone.ts`, `official-build.ts`, `accounts/`): official releases ask for a Gui account before a project opens; a build from source doesn't, and can still sign in from Settings. Sign-in happens in your browser against the account service (the Cloudflare Worker in `accounts/`, see its [README](../accounts/README.md)) and comes back to a loopback port Gui listens on. Main keeps the session in Gui's data folder, encrypted with the Keychain. Connecting GitHub to the account is only for cloning: Gui lists the repositories you chose, and each clone asks the service for a fresh token for that one repository (`RepoToken`). Account requests are taken from Gui's own UI only (the Settings window and a window's chrome), never the chat panel or a preview. [GitHub projects and accounts](github-accounts.md) has the journey.
- **Checkpoints** (`src/main/checkpoints.ts`): before and after every turn the working tree is snapshotted into a shadow git repo under the app's data folder (your `.git` is never touched). **Undo** on a message is the one way back: it restores the files that turn (and any later ones) changed to how they were before it; files you edited yourself are left alone. **Redo** reverses the undo, until the next message (an agent's turn or a text edit) clears it. ⌘Z and ⇧⌘Z do the same for the newest message while the chat shows. A folder inside the project with a git repository of its own is recorded only as a link to its commit, so undo and redo leave it exactly as it is, restore everything else, and say so on the message.
